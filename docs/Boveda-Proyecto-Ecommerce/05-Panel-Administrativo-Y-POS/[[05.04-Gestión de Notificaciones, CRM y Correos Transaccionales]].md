# [[05.04-Gestión de Notificaciones, CRM y Correos Transaccionales]]

## 1. Visión General

Este módulo es el "cerebro comunicativo" del sistema. Se encarga de enviar notificaciones automáticas en los momentos críticos del flujo de compra para que el cliente nunca se sienta desatendido.

## 2. El Ciclo de Notificaciones (Eventos)

El sistema debe tener plantillas pre-configuradas que se disparan según el `estado` del pedido:

* **Pedido Recibido (Pending):** Envío automático del enlace de pago manual (Proforma).
* **Pago Aprobado (Processing):** Envío de la boleta electrónica PDF y confirmación de recepción de fondos.
* **En Camino (Shipped):** Notificación con el número de seguimiento (tracking) del courier (Shalom/Olva).
* **Entrega Confirmada (Delivered):** Correo de seguimiento para asegurar que el producto llegó en buenas condiciones y pedir una reseña.
* **Alerta de Preventa (Stock Arrival):** Notificación automática a quienes reservaron un producto cuando este llega finalmente a almacén.

## 3. CRM: Ficha de Cliente (Perfil 360°)

Más allá de enviar correos, este módulo centraliza el historial del usuario:

* **Historial de Compras:** Total invertido por el cliente.
* **Nivel de Fidelidad:** Etiquetado manual o automático (ej. "Cliente VIP", "Coleccionista frecuente", "Cliente en riesgo").
* **Notas del Admin:** Campo de texto libre para que el admin deje recordatorios (ej. "Cliente prefiere que le escriban por WhatsApp antes de llamar").

## 4. Gestión de Listas (Opt-in Marketing)

* **Base de datos de suscritos:** Lista de correos de clientes que aceptaron recibir promociones (cumpliendo la Ley de Protección de Datos).
* **Seguimiento de Aperturas:** Estadísticas básicas (¿Cuántos clientes abrieron el correo de la preventa? ¿Cuántos hicieron clic?).

## 5. Campana de Notificaciones en Vivo ✅ (Implementado)

Se implementó una campana de notificaciones con **polling en vivo + alerta por correo**, tanto para el administrador como para el cliente:

### Admin (`NotificationBell.tsx`)
* Se refresca por polling, avisa de vouchers/abonos nuevos esperando aprobación en la Bandeja POS y de alertas de stock bajo/agotado (ver **[[05.03-Control de Inventario y Preventas]]**, sección 5).
* Además del aviso en vivo dentro del panel, se envía un **correo automático a `frizio.trabajo@gmail.com`** (bandeja del administrador) específicamente para eventos de **pagos y abonos** — no para cada evento del sistema, para no saturar el correo.

### Cliente (`UserNotificationBell.tsx`) — nuevo
* Aparece en el `Header` público solo si hay sesión iniciada.
* Deriva dos contadores **sin tabla de notificaciones propia** (se calculan al vuelo desde tablas existentes vía `/api/user/notifications`):
* **Mensajes sin leer:** `Message.count({ recipientId: user.id, readAt: null })`.
* **Pedidos en proceso:** `Order.count` con estado `PENDING` / `VERIFYING` / `PAID_APPROVED`.
* Se refresca por polling (30 s), al enfocar la pestaña y al disparar el evento `messages:updated` (por ejemplo, al leer un mensaje en la bandeja — ver sección 7).
* Cada ítem tiene un color de urgencia (`info` azul, `warning` amarillo, `critical` rojo) con un punto animado (*ping*), y el badge numérico parpadea si hay pendientes.

## 6. Sistema de Mensajería Interna Admin → Cliente ✅ (Implementado)

Más allá de los correos transaccionales automáticos, se construyó un canal de **mensajería directa dentro de la plataforma** para que el negocio pueda escribirle a un cliente (o a varios) sin depender de WhatsApp para todo.

### Modelo de datos
* `Sticker` (id, name, imageUrl, createdAt): catálogo de figuras/emojis de marca subidos por el admin.
* `Message` (id, recipientId, senderId, body, stickerId?, batchId?, readAt?, createdAt): un mensaje individual dirigido a **un solo usuario**.

### Difusión (fan-out)
El admin puede enviar un mensaje a:
1. **Un usuario específico** (con buscador por nombre/@usuario/email).
2. **Todos los clientes registrados.**
3. **Un segmento por nivel de lealtad** (`loyaltyTier`: Nuevos / Frecuentes / VIP / En riesgo).

Independientemente del destino, el sistema crea **una fila `Message` por destinatario** (`createMany`), todas compartiendo un mismo `batchId`. Esto evita normalizar una tabla de "listas de difusión" aparte y deja que la bandeja de "enviados" del admin agrupe por `batchId` mostrando cuántos de los destinatarios ya lo leyeron.

### Texto enriquecido seguro (sin HTML, sin librerías pesadas)
* El admin da formato con una barra de herramientas **Negrita / Cursiva / Tachado** que envuelve la selección con marcadores de texto plano: `**negrita**`, `*cursiva*`, `~~tachado~~`.
* El mensaje se guarda como **texto plano con marcadores**, nunca como HTML.
* El renderer (`MessageBody.tsx`, compartido entre bandeja del admin, preview y bandeja del cliente) tokeniza ese texto con una expresión regular y genera elementos React (`<strong>`, `<em>`, `<s>`) — **nunca usa `dangerouslySetInnerHTML`**. Queda a salvo de XSS por construcción, ya que React escapa cualquier texto que no reconozca como marcador.

### Stickers de marca
* El admin gestiona un catálogo propio en `/admin/stickers` (grid + botón "crear sticker" en página dedicada, subiendo un PNG a Cloudinary bajo `latiendita/stickers`, reutilizando la validación de subida existente — `sniffImageType`, 5 MB máx).
* Al eliminar un sticker se limpia también su imagen en Cloudinary (mismo `deleteImageByUrl()` de la sección 6 de **[[05.03-Control de Inventario y Preventas]]**).
* Al componer un mensaje, el admin puede adjuntar **un sticker** desde un selector visual (`StickerPicker`).

### Flujo de envío (admin)
* Página dedicada `/admin/messages/new` (acepta `?userId=` para prellenar destinatario desde la ficha 360° del cliente — botón "Enviar mensaje" en `/admin/users/[id]`).
* Vista previa en vivo del mensaje formateado + sticker antes de enviar.
* `/admin/messages` funciona como bandeja de **enviados**: lista por lote (`batchId`) con ícono según sea difusión o 1‑a‑1, y contador de leídos/total.

## 7. Bandeja del Cliente (leer mensajes) ✅ (Implementado)

* Página `/profile/messages`: lista tipo acordeón, con un punto azul animado en los mensajes no leídos y vista previa truncada (90 caracteres, sin marcadores de formato).
* Al abrir un mensaje se renderiza el cuerpo completo (`MessageBody`) + el sticker si tiene, y se marca `readAt` automáticamente (`PATCH /api/user/messages/[id]/read`), disparando el evento `messages:updated` para refrescar el badge de la campana y del sidebar de perfil en el mismo instante.
* **Aislamiento estricto:** el endpoint `GET /api/user/messages` solo devuelve mensajes donde `recipientId === session.user.id` — un usuario nunca puede ver mensajes de otro, incluso conociendo el `batchId`.

## 8. Seguridad del Módulo de Mensajería

* Rutas `/api/admin/messages*` y `/api/admin/stickers*` protegidas con `requireAdmin`.
* Rutas `/api/user/messages*` protegidas con `requireUser` + verificación explícita de propiedad (`recipientId`) en cada lectura y en el `PATCH` de "marcar leído".
* `body` del mensaje validado con zod (1–4000 caracteres); `name` del sticker (1–40 caracteres); `imageUrl` debe ser una URL `http(s)` o un `/uploads/` local — nunca datos arbitrarios.
